Admin → Communications publishes announcements to the banner and queues notifications for active portal accounts that existed when the announcement was created. Admin → Notifications and the contributor notification page show them; the bell shows unread counts. The page refreshes every 30 seconds while visible, and the bell every 60 seconds. Mark one or all notifications read without reloading.

Select **Also send to contributors’ email inboxes** to enqueue email as well. The default is off. Only active, verified contributors receive broadcast email, using the configured SMTP provider (including Gmail). Each message addresses one recipient; email addresses are not exposed to other recipients. The worker rechecks eligibility, current email, and announcement status before sending.

Run `npm run worker` from EpapersApi; restart an existing worker after this update. Notifications and email delivery require this worker. The API saves the announcement and queues jobs in one transaction, then returns without waiting for SMTP. No new database migration or credentials are required.

Delivery uses batches of 25 accounts, one email send slot every 10 seconds across worker processes, and a one-hour broadcast cooldown per recipient. SMTP broadcasts use at most 80% of SMTP_DAILY_LIMIT, leaving capacity for authentication and transactional email. Authentication email jobs keep priority. Throttle and quota deferrals do not exhaust retry attempts. Failed sends use the existing exponential retry policy and eventually become failed jobs. Inactive, deleted or expired announcements stop queued delivery. Future announcements wait until their start time.

POST `/api/v1/admin/announcements` accepts optional `sendEmail` (false by default) and `requestId` (UUID). The frontend keeps the request ID for retries of the same submission; editing the message generates a new one. Replaying an identical submission returns its original announcement; changing content while reusing the request ID returns 409. Job receipts prevent duplicate portal notifications and email enqueueing after lease recovery. As with other SMTP delivery, an uncertain network response after the mail server accepts a message can result in another delivery on retry; SMTP does not provide exactly-once delivery.

Queued email bodies remain encrypted. Completed email payloads are cleared after seven days by existing retention maintenance. Broadcast receipt jobs are retained for duplicate prevention. Inspect `jobs` for `broadcast_notifications` and `email_broadcast` statuses to diagnose delivery.

Actions use disabled controls, an accessible spinner/status, and a ref guard until completion. Identical concurrent API writes share one request; a top progress bar shows requests that take longer than 250 ms. Navigation links stay usable. Upload submission also guards against concurrent file uploads. Errors restore the controls and use the existing toast.
